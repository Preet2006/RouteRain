# Data Dictionary — `training_data.csv`

One row = one (hotspot, date) candidate rainy day (`rain_24h > config.RAIN_THRESHOLD_MM`, currently 10mm), built in Phase 6 by joining weather, terrain, and flood-label data.

| Column | Meaning | Unit | Source | Role |
|---|---|---|---|---|
| `hotspot_id` | Identifier for one of the 12 verified waterlogging hotspots (H01-H12) | - | `data/raw/hotspots.csv` (Phase 2) | identifier |
| `date` | Calendar date of the rain day | ISO date (YYYY-MM-DD) | Derived from Open-Meteo hourly timestamps (Phase 4) | identifier |
| `rain_24h` | Total precipitation that calendar date | mm | Open-Meteo Archive API, hourly precipitation summed per day (Phase 4) | feature |
| `rain_max_1h` | Peak single-hour precipitation that date | mm/hr | Open-Meteo Archive API (Phase 4) | feature |
| `rain_max_3h` | Peak rolling 3-hour precipitation sum that date | mm/3hr | Open-Meteo Archive API, rolling window over hourly series (Phase 4) | feature |
| `rain_prev_3d` | Trailing 3-day `rain_24h` sum, shifted by 1 day so the current day is excluded from its own antecedent window; computed within a single year's monsoon season only (does not bridge the Jun-Sep gap across years) | mm | Derived from `rain_24h` (Phase 4) | feature |
| `soil_moisture_surface` | Same-day mean of `soil_moisture_0_to_7cm` (ERA5-Land reanalysis). A direct ground-saturation measurement, distinct from the rainfall-as-proxy features above. Added to the permanent pipeline after a Phase 7 exploratory round found it ranked ~2nd in RandomForest feature importance and lifted test ROC-AUC by +0.059 -- outside this project's ~0.02-0.03 run-to-run noise margin. Confirmed available for the full 7-day forecast horizon with real (non-flat) variation before adoption | m3/m3 (volumetric fraction) | Open-Meteo Archive/Forecast API, same call as precipitation (Phase 4) | feature |
| `rain_season_cumulative` | Total `rain_24h` for that hotspot, summed from June 1 of that date's year through the current date (inclusive). Captures whole-season ground saturation beyond the 3-day window of `rain_prev_3d` | mm | Derived from the full `weather_features.csv` series (Phase 6, added after the original Phase 7 run showed terrain features carried little signal) | feature |
| `hotspot_flood_rate_prior` | Smoothed historical flood rate for this hotspot: `(flooded_count_train + 5*global_train_rate) / (candidate_days_train + 5)` (Laplace smoothing, k=5), computed **only from 2022-2024 training-period rows**, then applied as a fixed constant to every row for that hotspot in both train and test. Verified identical across all of a hotspot's rows regardless of year (Phase 6 leakage check) | probability (0-1) | Derived from `flooded` + training-period row counts, per hotspot (Phase 6) | feature |
| `has_infrastructure_issue` | Binary flag: 1 if this hotspot has documented evidence of a *specific, structural* infrastructure defect (choked drain, cave-in, sinkhole, pump failure) rather than generic citywide flood response. Only H01, H02, H04, H05, H12 are flagged 1; the other 7 are 0. Static per hotspot, not leakage-sensitive (not derived from flood outcomes) | binary (0/1) | `data/raw/infrastructure_issues.csv`, manually curated from `flood_events.csv` notes (Phase 6) | feature |
| `elevation_m` | DEM elevation at the hotspot's exact coordinate | meters | SRTM 1-arc-second DEM (`gurugram_ncr.tif`), via AWS public Terrain Tiles mirror (Phase 3) | feature |
| `slope_deg` | Local slope estimate: `degrees(arctan(nanstd(window) / pixel_size_m))` over a `TERRAIN_RADIUS_CELLS`-radius DEM window. numpy-only fallback (richdem failed to build on this platform, Phase 1/3) -- a proxy for terrain roughness, not a true slope algorithm | degrees | Derived from DEM (Phase 3) | feature |
| `sink_depth_m` | `mean(window elevation) - elevation_at_point`. Positive = the point sits lower than its local surroundings (a topographic sink); negative = the point sits higher (a local high point/ridge) | meters | Derived from DEM (Phase 3) | feature |
| `catchment_cells` | Count of DEM window cells with elevation higher than the hotspot's own elevation -- a simple proxy for contributing catchment area, not a real flow-accumulation algorithm | count (cells) | Derived from DEM (Phase 3) | feature |
| `month` | Calendar month of `date` (6-9 for June-September) | integer (6-9) | Derived from `date` | feature |
| `flooded` | 1 if a documented flood event at this hotspot matched this date within `DATE_MATCH_TOLERANCE_DAYS` (1 day); 0 otherwise (no matching reported event) | binary (0/1) | `data/processed/flood_labels_clean.csv`, manually researched news events (Phase 5) | **target** |

## Known limitations of this table (see also `LIMITATIONS.md`, Phase 11)

- **`flooded=0` means "no documented event found," not "confirmed dry."** Labels come from manually researched news coverage, which under-reports real flooding, especially at less-covered hotspots (H06, H12).
- **Rainfall is a single-point gridded estimate** (Open-Meteo, ~interpolated resolution), not a ground rain-gauge reading. It can disagree with news-reported citywide rainfall figures by several mm, which matters right at the `RAIN_THRESHOLD_MM` boundary (see Phase 6 report for specific near-miss examples).
- **`slope_deg` and `catchment_cells` are approximations**, not outputs of a real hydrological flow model -- `richdem` (which would provide proper flow accumulation / slope) failed to build on this project's platform (Phase 1).
- **A hotspot's terrain reading does not capture infrastructure-caused flooding** (e.g. a chronically choked drain) -- see the Phase 3 report's note on H01 Bilaspur Chowk, whose near-neutral `sink_depth_m` is consistent with its documented cause being blocked drainage, not topographic sinking.
- **Re-running the full pipeline does not reproduce bit-for-bit identical RandomForest results, even on numerically identical data.** An exploratory run and the final production-pipeline run disagreed on test AUC (0.6463 vs. 0.6380, a 0.0083 gap). Isolated and confirmed the cause directly: refitting the regenerated data with the exploratory round's exact hyperparameters (`n_estimators=100, max_depth=6, min_samples_leaf=1, min_samples_split=10`) recovers 0.6452 -- almost the full gap. **The dominant cause is ordinary hyperparameter-tuning variance**: the automatic time-aware grid search landed on a slightly different, slightly worse combination this run (`min_samples_leaf=3` instead of `1`), not a data or pipeline defect. A much smaller secondary effect (~0.001) comes from RandomForest's per-split random feature subsampling being sensitive to feature-column order under a fixed `random_state`, confirmed separately by holding hyperparameters fixed and only reordering columns (0.6463 -> 0.6452). Both are real, explained, and within the project's established ~0.02-0.03 noise margin -- not evidence of a bug.
